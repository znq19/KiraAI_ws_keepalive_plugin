# KiraAI_ws_keepalive_plugin

**WS 保活调优插件** —— 让 KiraAI 连接 OneBot (SnowLuma / NapCat) 时不再因为一次卡顿就误判断线。

作者：znq19 ｜ 版本 1.0.0 ｜ 适配 KiraAI `>= 2.29.6`

---

## 它解决什么问题

### 症状

KiraAI 日志里反复出现：

```
websockets.exceptions.ConnectionClosedError: sent 1011 (internal error)
    keepalive ping timeout; no close frame received
```

随后连接断开、重连，期间**丢消息、延误回复**。

### 根因

KiraAI 的 OneBot 适配器在连接时把保活参数写死了
（`core/adapter/src/qq/napcat_client/client.py`）：

```python
await ws_compatible_connect(..., ping_timeout=10.0)
```

`websockets` 库的保活跑在一个独立 task 里：

1. 每 `ping_interval` 秒发一个 ping
2. 然后最多等 `ping_timeout` 秒要 pong
3. 等不到 → 判定 `keepalive ping timeout` → 发 1011 → **断开**

**关键**：这个等待和应用代码共享**同一个 asyncio 事件循环**。
只要事件循环被占住超过 `ping_timeout`，pong 就处理不及时。

会占住事件循环的是**同步阻塞**操作（同步 I/O、CPU 密集计算、`time.sleep`
类调用），以及让**消息接收队列来不及消费**的持续高压 —— `websockets` 在
待收队列堆积时会暂停读取 socket，pong 也就读不进来。

**注意**：纯 `await` 的网络调用（`httpx.AsyncClient`、`AsyncOpenAI` 等）
在等待时**会正确让出事件循环**，本身不是元凶。真正要警惕的是同步调用。

10 秒对这个进程本来就偏紧：它同时要处理消息、调 LLM、下图片、写数据库，
任何一处短暂停顿都容易顶到上限。

> 补充：插件只放宽容忍度，**不伪造心跳**。真正的断线（网线拔了、进程死了）
> 照样会被发现并重连 —— 只是不再因为"只是慢了一下"而误判。

### 本插件做什么

**不改 KiraAI 任何源码**，把保活预算放宽：

| 参数 | 原值 | 默认新值 | 效果 |
|---|---|---|---|
| `ping_timeout` | 10.0 | **30.0** | 等 pong 的容忍度 ×3 |
| `ping_interval` | 20.0 | 20.0 | 心跳频率（不变） |
| `open_timeout` | 5.0 | **10.0** | 建连/握手容忍 ×2 |

## 安装

把插件文件放进 KiraAI 的插件目录，例如：

```
KiraAI/plugins/KiraAI_ws_keepalive_plugin/
    ├── main.py
    ├── manifest.json
    ├── schema.json
    ├── icon.png
    └── README.md
```

> 目录名**不影响功能** —— 插件身份由 `manifest.json` 里的 `plugin_id`
> （`ws-keepalive`）决定。直接 clone / 解压仓库后整个文件夹丢进 `plugins/` 即可。

然后**重启 KiraAI**。在 Web 面板的插件列表里应能看到 **「WS Keepalive 保活调优」**。

## 配置项

所有配置都在 Web 面板里，带中文说明。

### 保活参数

| 配置项 | 默认 | 说明 |
|---|---|---|
| `ping_timeout` | 30 | **关键参数**。等 pong 的最长时间 |
| `ping_interval` | 20 | 心跳频率，一般不用动 |
| `open_timeout` | 10 | 建连/握手超时 |

**调参建议**：
- 默认 **30 秒**已能覆盖绝大多数卡顿
- 机器很忙可调到 **45~60**
- **不建议超过 120**：太长会让"真断线"的发现变慢
  （不过检测真断线主要还是服务端的事，SnowLuma 会处理）

### 高级

| 配置项 | 默认 | 说明 |
|---|---|---|
| `debug_log` | false | 输出调试日志（日志里搜 `[ws-keepalive]`） |

> **没有开关能关掉自动应用**：挂钩与巡检是插件的本职，且开销可忽略
> （见下）。想停用就停用/删除插件本身。

## 它是怎么做到的

两个动作，互补覆盖：

### ① 挂钩连接函数（覆盖新建 + 所有重连）

包装适配器内部的连接函数，让**每一次**建连都带上调优后的参数：

```python
# core/adapter/src/qq/napcat_client/client.py 里
def ws_compatible_connect(uri, *, extra_headers, **kwargs):
    kwargs["ping_timeout"] = plugin.ping_timeout     # 覆盖硬编码的 10.0
    kwargs["ping_interval"] = plugin.ping_interval
    kwargs["open_timeout"] = plugin.open_timeout     # 覆盖硬编码的 5.0
    return original(uri, extra_headers=extra_headers, **kwargs)
```

> **为什么是直接赋值而不是 `setdefault`？** 适配器对这三个参数都传了**显式值**
> （`ping_timeout=10.0`、`open_timeout=5.0`），而 `setdefault` 只在**键缺失**时
> 才生效 —— 用 `setdefault` 的话 `open_timeout` 根本改不动（早期版本踩过这个坑）。

> **为什么挂函数而不是方法？** 因为 KiraAI 的初次连接和每次重连**都**走
> `NapCatWebSocketClient.connect`，而它内部调这个函数 —— 挂一处全覆盖。

### ② 巡检已建立的连接

`ping_timeout` 等参数是 websockets 连接对象上的**普通实例属性**，可直接改：

```python
ws.ping_timeout = 30.0
```

每 15 秒巡检一次，兜住两种情况：
- 插件加载时连接**已经建立**了
- 任何绕过挂钩的重连

### 设计原则

- **只放宽容忍度，绝不伪造心跳** —— 真断线照样被发现
- **零侵入** —— 不修改 KiraAI 任何源码文件
- **零 LLM 面** —— 不注册任何工具 / page / tag，模型无需感知它的存在。
  保活超时是基础设施参数，不该由模型管理；实测在真实框架下**注册组件数 = 0**
- **可回退** —— 插件停用/卸载时还原原始连接函数
- **全自动** —— 挂钩覆盖所有建连，巡检持续兜底，没有"半开"的中间状态

## 性能与稳定性

### 开销实测（同一台机器基准对比）

| 项目 | 实测 |
|---|---|
| 每次**建连**多花 | **0.66 µs** |
| 每次**巡检**（1 个适配器） | **1.5 µs** |
| 每次巡检（10 个适配器，最坏情况） | **9.6 µs** |
| 后台任务 | 增加 **1 个**（巡检循环），停止后 **0 残留** |

**换算**：巡检每 15 秒跑一次 1.5 µs ⇒ 占用时间比例约 **0.000011%**。
而且建连是**低频事件**（只在启动/重连时发生），不在消息收发热路径上。

### 为什么它不会引入新的不稳定

| 关注点 | 说明 |
|---|---|
| 会不会拖慢消息收发？ | **不会**。挂钩只包**建连函数**，消息收发完全不经它 |
| 改活连接会不会搞坏 websockets？ | **不会**。`ping_timeout` / `ping_interval` 是 `keepalive()` 循环**每轮现读**的普通属性，改动下个周期自然生效 |
| 异常会不会漏出来？ | 所有钩子路径都有 try/except + 日志（debug 级），不影响主流程 |
| 会不会泄漏任务/内存？ | 已测：启动 +1 个任务，停止后归零；无累积 |
| 值已正确时会不会反复写？ | 会比较，相同则跳过（实测「刷新 0 个」） |

### 一个诚实的权衡

**放宽 `ping_timeout` 会让「真正的死连接」发现得慢一些**：
从 10 秒变成 30 秒（+20 秒）。

但要说清楚：
- 如果对端是**进程死掉/网络断开**，TCP 层会立刻报错 → `close` 事件立即触发重连，
  **轮不到 ping 超时**，所以这种情况**不受影响**
- 只有「写得进去、读不回来」的**半开**状态才由 ping 超时兜底 —— 这时多等
  20 秒的代价，换来的是**大幅减少误判**（原本 10 秒预算太紧，正常卡顿就会中招）

这个取舍是插件存在的意义：**把「频繁误判」换成「偶尔慢一点发现」**。

## 诚实说明：能保证不断线吗？

**不能 100% 保证，但能大幅减少。**

本插件消除的是**「10 秒预算太紧」**这个诱因。如果 KiraAI 某次卡顿
**超过你设置的 `ping_timeout`**（比如设 30 秒、而某次 LLM 调用卡了 76 秒），
**还是会断**。

要彻底解决，建议**组合**：

1. ✅ **本插件** —— 放宽容忍度，消除绝大多数误判
2. ✅ **SnowLuma 侧补丁** —— 保证服务端**绝不主动断开**慢客户端
   （SnowLuma 的心跳容忍度是 ~90 秒，远宽于客户端的 10 秒，
   所以它永远不会比客户端先判死）
3. ⚠️ **排查 KiraAI 里真正长时间阻塞的地方** —— 例如给耗时的 LLM 调用
   加超时、或把同步阻塞改成异步。这一步需要按实际日志定位。

前两层已经能挡掉绝大多数断线。第三层是"如果还断，去找是谁卡住了"。

## 排错

### 插件加载了但没生效？

1. 打开 `debug_log`，重启后在日志里搜 `[ws-keepalive]`
2. 应该能看到：
   ```
   [ws-keepalive] 已应用保活调优: ping_timeout=30.0s ping_interval=20.0s open_timeout=10.0s（覆盖新建连接与所有重连）
   ```
3. 再看一条 `建立连接: ...`（每次建连/重连都会打），确认参数已是调优后的值

### 日志说"无法挂钩连接函数"？

说明你的 KiraAI 版本里 `ws_compatible_connect` 位置不同。
插件会退化为**只调优已建立的连接**（仍然有用）。
把 KiraAI 版本号提个 issue，我来适配。

### 想恢复默认行为？

把插件停用（或删掉），或在面板里把 `ping_timeout` 改回 10。
